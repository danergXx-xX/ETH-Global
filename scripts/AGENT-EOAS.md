## Schemat seeda (PUBLIC, testnet only)

```
seed       = "aitc-<persona>-2026-v1"
privateKey = keccak256(toHex(seed))    // 32 bajty -> valid secp256k1 priv
address    = privateKeyToAccount(privateKey).address
```

Komponenty:
- `aitc` - namespace projektu (AI Treasury Council)
- `<persona>` - jeden z `bull`, `bear`, `risk`, `tech`, `sentiment`
- `2026` - rok rotation marker
- `v1` - schema version (publiczny dla testnet, sekretny dla mainnet)

## Verify these are NOT precompiles (juror smell test)

EVM precompiles to addresses `0x0000...0001` do `0x0000...0009` (ecrecover,
sha256, ripemd160, identity, modexp, ecadd, ecmul, ecpairing, blake2f). Jesli
juror chce zweryfikowac ze ai.address NIE jest precompile:

1. **Compare leading bytes:** precompile = 19 leading zero bytes + 1 byte
   value 0x01-0x09. Nasze addresses = 20 bajtow pseudo-losowych z keccak256
   derywacji - leading byte to `0xB0`, `0x9C`, `0x16`, `0x87`, `0xbD` (zaden &lt;= 0x09).

2. **Replicate seed:** uruchom snippet ponizej, otrzymasz BYTE-IDENTICAL address.
   Precompiles NIE pochodza z private key - to hardcoded EVM behavior.

3. **Check derivation path:** `keccak256(toHex(seed))` -> 32 bajty -> last 20 bajtow
   keccak256(publicKey) = address. Standard secp256k1, nie hardcoded EVM.

## Backend signing (jesli kiedys potrzebne)

**Prawda o env vars:** `BACKEND_AGENT_<PERSONA>_PK` env var pattern jest
**REDUNDANT** dopoki seed jest publiczny - backend moze derywowac PK ze seeda
lokalnie w pamieci (`derivePrivateKey(persona)` z `scripts/lib/agent-eoas.ts`).
Trzymanie PK w Railway env vars dodaje attack surface bez korzysci.

Pattern jest dokumentowany TYLKO jako placeholder na wypadek mainnet rotation,
gdzie:
- Seed bedzie sekretny (nie w repo)
- Wtedy backend NIE moze derywowac sam - PK musza byc dostarczone przez secret store
- Wtedy `BACKEND_AGENT_<PERSONA>_PK` env var ma sens

Na testnet: NIE konfigurujemy tych env vars, backend uzywa `derivePrivateKey`
bezposrednio (jesli kiedykolwiek bedzie podpisywal - obecnie agenci nie podpisuja
on-chain, tylko Dan jako parent owner).

## Address override (escape hatch)

`BACKEND_AGENT_<PERSONA>_ADDR` env var nadpisze derived address (uzyteczne gdy
zamiast EOA chcesz multisig / smart account). `scripts/lib/agent-eoas.ts::getAgentAddress()`
honoruje override.

## Why deterministic, not random?

Random keys = jednorazowe + ryzyko zgubienia (catastrophic loss). Determi-
nistic seed pattern:
1. Pelne **reproducibility** - kazda osoba w teamie odtwarza addresses
2. **Disaster recovery** - jesli wallet pliki zniknije, regeneracja w 1s
3. **Audytowalnosc** - juror moze zweryfikowac ze addresses pochodza z
   konkretnego seeda, nie z secret stash
4. **Brak BIP39 dependency** - lzejsze toolowanie (tylko viem)

## Mainnet migration (post-hackathon decision, NIE robimy teraz)

Jesli kiedys cos z tego pojdzie na mainnet:
1. `SEED_VERSION` z `v1` na `v2`
2. Nowy seed string trzymany **POZA repo** (1Password vault, lub Railway sealed
   secret jako `BACKEND_SEED_SALT`)
3. `agent-eoas.ts` czyta seed salt z env, fallback na `v1` blokowany w prod
4. Re-deploy ENS subnames z nowymi addresses
5. Multisig zamiast raw EOA dla agent-controlled funds (limit blast radius)
6. Hardware wallet dla parent ownership (zamiast hot ENS_OWNER_PRIVATE_KEY)
